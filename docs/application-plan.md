# แผนพัฒนาแอปจัดการราคาและเอกสารการขาย

## เป้าหมายและจุดเริ่มต้น

ให้ฝ่ายขายค้นสินค้า เลือกราคาที่ใช้ได้ จัดทำและอนุมัติใบเสนอราคา แล้วส่งต่อให้ผู้รับผิดชอบออกใบแจ้งหนี้และใบวางบิล พร้อมประวัติที่ตรวจย้อนกลับได้

โปรเจกต์ปัจจุบันเป็น Next.js 16.3.4 / React 19.2.8 / TypeScript / Tailwind 4 มี dashboard และหน้า auth ตัวอย่าง ยังไม่พบฐานข้อมูล ORM หรือ backend งานขายจากไฟล์ที่ตรวจ จึงเสนอใช้โครง UI เดิมและเพิ่ม business modules ตามลำดับ

แบบตารางและกติกา: [database-design.md](database-design.md)

## โมดูลและผู้ใช้

| โมดูล | ความสามารถรุ่นแรก | ผู้ใช้หลัก |
|---|---|---|
| ผู้ใช้และสิทธิ์ | เข้าระบบ ปิดบัญชี กำหนดบทบาทและสิทธิ์ | Admin |
| ลูกค้า | บริษัท/บุคคล สาขา ผู้ติดต่อ เครดิต เงื่อนไขวางบิล | Sales, Accounting |
| สินค้า | รหัส รุ่น Part Number ประเภท หน่วย รายละเอียด Warranty | Admin, Sales ตามสิทธิ์ |
| Price List | นำเข้า ตรวจข้อมูล version วันเริ่ม/หมดอายุ ราคาขายและฐานภาษี | ผู้จัดการราคา |
| ใบเสนอราคา | เลือกลูกค้า เพิ่มหลายรายการ คำนวณส่วนลด/ภาษี อนุมัติ revision พิมพ์ PDF | Sales, Manager |
| ใบแจ้งหนี้ / Invoice | สร้างจาก accepted quotation ตรวจยอดและแหล่งที่มา ออกเลข พิมพ์ | Accounting |
| ใบวางบิล | เลือกหลาย Invoice ของลูกค้ารายเดียว ออกเอกสารตามรอบ | Accounting |
| ตั้งค่าและประวัติ | ข้อมูลบริษัท เลขเอกสาร template audit และผลนำเข้า | Admin |

ลูกค้าเป็นโมดูลที่เพิ่มจากข้อมูลจริงใน Excel; ชื่อ Invoice ยังเป็นสมมติฐาน ถ้าหมายถึงใบกำกับภาษีจะเพิ่มเมนูและขั้นตอนเฉพาะก่อนวางบิลตามกระบวนการที่ยืนยัน

## สิทธิ์ที่เสนอ

- Sales: จัดการลูกค้าและใบเสนอราคาของตน ดูราคาขาย แก้ราคาตามสิทธิ์ ส่งขออนุมัติ
- Manager: ดูงานขายตามขอบเขต อนุมัติส่วนลด/ราคา อนุมัติข้อเสนอ; ค่าเริ่มต้นไม่อนุมัติคำขอของตนเอง
- Accounting: ออกใบแจ้งหนี้/ใบวางบิล ดูข้อมูลลูกค้าที่จำเป็น ยกเลิกตามนโยบาย
- Admin: จัดการบัญชีผู้ใช้และตั้งค่า การเห็นต้นทุนหรืออนุมัติเอกสารต้องเป็น permission ที่ชัดเจน

ตรวจทุก action ที่ server ทั้งการดู แก้ไข export และดาวน์โหลดไฟล์ ไม่อาศัยการซ่อนเมนู ปิด field ต้นทุนออกจาก response เมื่อไม่มี `price.cost.read` และตรวจ ownership ของเอกสารเมื่อเปิดด้วย URL โดยตรง

## โครงสร้างแอปที่เสนอ

```text
app/
  (sales)/customers/ products/ price-lists/ quotations/
  (accounting)/invoices/ billing-notes/
  (admin)/users/ settings/ imports/
modules/
  customers/ products/ pricing/ quotations/ invoices/ billing/
  documents/ imports/ authorization/
lib/
  db/ auth/ decimal/ storage/
```

แต่ละ module แยก input validation, service ที่ใช้กติกาธุรกิจ, repository และ components ตามจำเป็น ใช้แอปเดียวและ PostgreSQL เดียวในช่วงแรก ไม่ต้องแยก microservices

- Server Components โหลดข้อมูลเริ่มต้น; Client Components ใช้กับตารางเลือกสินค้าและฟอร์มที่โต้ตอบ
- Server Actions สำหรับฟอร์มภายใน; Route Handlers สำหรับ import/export/download และการเชื่อมระบบภายนอกในอนาคต
- เลือก database adapter/ORM ตอนเริ่ม migration โดยต้องรองรับ numeric, transactions, row locking และ SQL migration ที่ตรวจทานได้
- สร้าง calculation service ร่วมให้ใบเสนอราคาและ Invoice รวมถึง validator และสถานะเอกสาร เพื่อไม่คัดลอกสูตรหลายแห่ง
- PDF สร้างจาก snapshot และ version ของ template รองรับภาษาไทย หลายหน้า รายละเอียดบริการยาว ลายเซ็น และยอดรวม; เก็บ PDF ที่ออกแล้วใน private storage
- ใช้ worker/outbox เมื่อ import หรือ PDF เกินเวลาคำขอ โดยการออกเอกสารต้อง commit สำเร็จแม้ PDF ล้มเหลวและ retry ได้ด้วยข้อมูลฉบับเดิม
- ความลับและ DB credentials อยู่ server; แยก runtime DB role ออกจาก migration role; สำรองและทดลอง restore ก่อนเปิดใช้
- อ่านคู่มือที่ติดตั้งใน `node_modules/next/dist/docs/` ก่อน implementation ตาม AGENTS.md โดยเฉพาะ data-security, authentication และ Server Actions

## ขั้นตอนทำงาน

```mermaid
flowchart LR
    A[ลูกค้าและสินค้า] --> B[Price List ที่ใช้ได้]
    B --> C[ใบเสนอราคาร่าง]
    C --> D[อนุมัติภายใน]
    D --> E[ส่งให้ลูกค้า]
    E --> F[ลูกค้ายืนยัน]
    F --> G[ใบแจ้งหนี้ / Invoice]
    G --> H[รวบรวมใบวางบิล]
    H --> I[รับชำระ: ส่วนขยายหรือระบบบัญชี]
```

การส่งใน workflow หมายถึงบันทึกสถานะและดาวน์โหลดเอกสารสำหรับส่งเองก่อน หากต้องการอีเมลอัตโนมัติให้เพิ่มขอบเขตแยก

## แผนนำเข้า Excel

1. Upload → ตรวจชนิด/ขนาดไฟล์ → เก็บ checksum และ batch → อ่านเข้า staging โดยเก็บ sheet และ row เดิม
2. แสดง preview, mapping และ error ให้ผู้รับผิดชอบแก้ก่อน commit ป้องกันไฟล์เดิมถูกนำเข้าซ้ำด้วย checksum + mapping version
3. Customer: A→customer_code, B→is_active, C→tax_id, D→legal_name, E→credit_days, F/G→เงื่อนไขวางบิล/รับเงิน, H/I→branch/address, J:L→contact, M→notes
4. Price List: A:C→model/description/vendor_part; D:H→ราคาและฐานภาษี; I→remark; J/K→type/category; L→warranty; M→สถานะที่ต้อง normalize; N→วันหมดอายุ; O→uploaded_at เดิมที่ต้องตรวจ ไม่ใช้แทนเวลานำเข้าใหม่
5. Quotation: map หัวจากชีต Quotation และรายการจาก Quotation by items ผ่านเลขเอกสารที่ผ่านการแก้ปัญหาซ้ำแล้ว คงลำดับรายการตามแถวต้นฉบับ
6. หา customer_id ผ่าน mapping ที่ยืนยันแล้ว; ชื่อ salesperson นำเข้าเป็น historical display name และให้จับคู่กับผู้ใช้ ห้ามสร้างบัญชี login ใช้งานได้จากชื่อใน Excel
7. สินค้าที่ไม่สามารถจับคู่แน่นอนได้เก็บรายการพร้อม snapshot และ product_id=null จนกว่าจะมีผู้ยืนยัน ไม่ใช้ชื่อใกล้เคียงเพื่อผูกอัตโนมัติ
8. ตรวจยอดแต่ละเอกสารหลังส่วนลดท้ายบิล ฐานภาษีและการปัดเศษ แสดงผลต่างทั้งก่อนและหลัง normalize เลข QT ซ้ำต้องพักทั้งกลุ่มไว้
9. เก็บสถานะต้นฉบับแยก; ข้อมูลเก่าออกเอกสารแบบ read-only legacy หากยังพิสูจน์กติกาการคำนวณไม่ได้ ไม่สร้าง approval หรือ invoice transaction ย้อนหลังจากการเดา
10. Commit ต่อเอกสารใน transaction; batch รายงานสำเร็จ/รอตรวจ/ไม่ผ่าน ตรวจย้อนจาก record ไปยังไฟล์และแถวได้ จำนวนข้อมูลก่อน/หลัง reconcile ต้องตรงตามการแก้ปัญหาที่บันทึกไว้

ไม่ใช้วันที่ผิดเป็นวันนี้ ไม่เติม null เป็น 0 และไม่คำนวณทับยอดใน Excel โดยไม่มีรายงานความต่าง ข้อมูลต้นฉบับทั้งสามไฟล์คงเดิม

## ลำดับพัฒนาและเกณฑ์ผ่าน

| ระยะ | งาน | เกณฑ์จบ |
|---|---|---|
| 0: ตกลงกระบวนการ | นิยาม Invoice, สิทธิ์ราคา, กฎอนุมัติ, รูปแบบเลขและ PDF, ขอบเขตรับชำระ | ตอบข้อที่กระทบ schema และมีตัวอย่างเอกสารที่คาดหวัง |
| 1: พื้นฐาน | PostgreSQL migration, auth, permissions, บริษัท/สาขา, audit | login จริง ตรวจสิทธิ์ server ได้ และ migration/restore ทดลองผ่าน |
| 2: ข้อมูลหลัก | ลูกค้า สินค้า หน่วยหมวดหมู่ และ import staging | นำเข้า Customer พร้อมผลตรวจ เปิดข้อมูลและแก้ไขตามสิทธิ์ได้ |
| 3: ราคา | Price List versions, import และการเลือก effective price | ราคาเก่าไม่เปลี่ยน ราคา expired/unknown ไม่ถูกเลือกอัตโนมัติ ต้นทุนไม่รั่ว |
| 4: ใบเสนอราคา | calculation service, approval, revision, เลขเอกสาร, PDF | ทำใบเสนอราคาจริงได้ครบ มี PDF ภาษาไทยและหลักฐานอนุมัติ |
| 5: Invoice | convert จาก accepted revision, ตรวจซ้ำ/จำนวน, cancellation, PDF | ออกซ้ำจาก retry ไม่ได้ ราคาที่ตกลงคงเดิม |
| 6: ใบวางบิล | รวม Invoice, ตรวจลูกค้า/สกุลเงิน, รอบวางบิล, PDF | ไม่มีการจอง Invoice ซ้ำและยอดตรงกับเอกสารที่เลือก |
| 7: ทดลองใช้ | นำเข้าประวัติ UAT สำรอง/กู้คืน logging และคู่มือ | ฝ่ายขาย/บัญชีรับรองยอดและเอกสารก่อนเปิดใช้ |

จุดส่งมอบแรกที่ใช้งานได้คือจบระยะ 4: ผู้ใช้ + ลูกค้า + สินค้า + ราคา + ใบเสนอราคา ส่วนใบแจ้งหนี้และใบวางบิลตามในระยะ 5–6 หากต้องแสดงยอดค้างจริง ต้องรวมรับชำระ/การเชื่อมระบบบัญชีในระยะนั้นด้วย

ยังไม่ประเมินวันส่งมอบแบบตายตัวจนยืนยันขอบเขต PDF, Invoice, การรับชำระ และจำนวนผู้พัฒนา

## กรณีทดสอบที่มีผลต่อธุรกิจ

- ตัวอย่าง `QT-260831004`: 3 × 18,000 + 1 × 10,000 = 64,000; VAT ตามข้อมูลตัวอย่าง 4,480; ยอด 68,480 ต้องตรงทั้ง API, DB และ PDF
- ราคาที่รวม VAT, ส่วนลดรายบรรทัด/ท้ายบิล, หลายอัตราภาษี, รายการยกเว้น และการจัดเศษส่วนลดต้องรวมตรงกัน
- WHT ลดเงินคาดรับตามฐานที่กำหนด ไม่ลด grand_total ของข้อเสนอ; รับชำระบางส่วนไม่ปิดหนี้เกินจริงเมื่อเพิ่มโมดูลรับเงิน
- เปลี่ยนที่อยู่ลูกค้าหรือ Price List แล้วเอกสารที่ออกก่อนหน้าและ PDF เดิมต้องไม่เปลี่ยน
- ส่งอนุมัติแล้วแก้ราคา ต้องทำ revision/อนุมัติใหม่; ผู้ขายอนุมัติตนเองไม่ได้ตามนโยบายที่กำหนด
- ผู้ใช้สองคน issue พร้อมกันเลขไม่ซ้ำ; double click/retry ได้เอกสารเดิม; stale edit ถูกปฏิเสธด้วย row_version
- แปลงใบเสนอราคาเป็น Invoice พร้อมกันไม่เกินจำนวน; ไม่อ้าง source item จากคนละ revision
- สองคนเลือก Invoice เดียวกันวางบิล ต้องมีคนหนึ่งได้รับแจ้ง conflict; ยกเลิกแล้วนำกลับวางบิลได้ตามกติกา
- Sales ไม่เห็นต้นทุนผ่านหน้าเว็บ API export หรือ URL ไฟล์; ผู้ไม่มีสิทธิ์เข้าถึงเอกสารรายอื่นไม่ได้
- นำเข้า Excel รอบสองไม่สร้างซ้ำ, วันที่ผิดพักไว้, QT-210610002 ไม่ถูกทับ, ผลต่างจากส่วนลดไม่ถูกระบุว่าข้อมูลเสียโดยทันที
- PDF หลายหน้าไม่ตัดชื่อสินค้า/รายละเอียด/ยอดรวม ภาษาไทยแสดงครบ และยอดตรงกับ snapshot

## สิ่งนอกขอบเขตรุ่นแรกที่ต้องเลือกเพิ่ม

สต็อก จัดซื้อ ต้นทุนเฉลี่ย ส่งของแยกรายการ ใบเสร็จ/รับชำระ ใบลดหนี้/เพิ่มหนี้ e-Tax การลงบัญชีแยกประเภท หลายสกุลเงิน และ multi-tenant ไม่ถือว่ารวมใน CRUD งานขายโดยอัตโนมัติ

หากการใช้งานจริงต้องใช้ใบกำกับภาษี ใบเสร็จ หรือใบลดหนี้ ให้จัดไว้ในขอบเขตก่อนเปิดใช้งานธุรกรรมส่วนนั้น และให้ผู้รับผิดชอบบัญชีตรวจเนื้อหาเอกสารและกติกาที่เกี่ยวข้อง
